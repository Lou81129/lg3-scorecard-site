Bug Fixes — Shade Button & Print Both Team Rules (v95.23)

Bug 1 — Duplicate Shade Toggle Button

Two identical Shade: Par 3 buttons appeared side by side in the control bar. Only the first was wired to the event listener — the second was completely non-functional.

  • Root cause: duplicate id="btn-shade-toggle" button element in the HTML
  • Fix: second duplicate button removed — one button, correctly wired

Bug 2 — Print Both Reveals Team Rules Boxes on Screen

When Print Both was used on an individual card, the Scramble and Chapman team rules boxes became visible on screen immediately after the PDF was captured — they did not print but were visible.

  • Root cause: after PDF capture, buildPairedPDF and generate2UpPDF restored the team rules divs to display:'' (empty string) — clearing the inline style handed control back to the CSS default (display:block), making both boxes visible
  • Fix: both functions now explicitly restore to display:'none'
  • Team rules boxes are invisible before, during, and after all print operations when on individual cards

Bug Fix — Shade Toggle Double Listener (v95.24)

After the duplicate HTML button was removed in v95.23, the shade toggle still failed to work. Clicking the button appeared to do nothing.

  • Root cause: two addEventListener calls were bound to btn-shade-toggle in JavaScript. Each click fired P5_MODE=!P5_MODE twice — toggling on then immediately back off. Net result: no visible change
  • The second listener was an incomplete duplicate — it was missing the P3G/P3N column header rename logic entirely
  • Fix: second (incomplete) listener removed; the first, complete listener retained

Bug Fix — P5G / P5N Column Headers Reset on Print (v95.25)

When Par 5 shade mode was active, the P5G / P5N column headers displayed correctly on screen but reverted to P3G / P3N on the printed scorecard.

Root Cause

The Par 5 shading carried through print correctly because it is CSS-class based (body.p5-shade) — a class that survives any table rebuild. The column header text, however, is DOM text content — reset to "P3 G" / "P3 N" every time buildTable() runs, including on every print and PDF rebuild path.

Fix

  • buildTable() now checks P5_MODE immediately after generating the header row and applies "P5 G" / "P5 N" on the spot
  • Every rebuild — screen, Print Card, Print Both, Print All — now always reflects the active shade state
  • Toggling back to Par 3 mode restores P3 G / P3 N correctly on all paths

Gender-Aware Course Handicap Calculation (v95.26)

Course Handicap calculations now correctly use Ladies' course ratings and slope when a female player is in the group. Previously all players were calculated against Men's ratings regardless of gender.

Gender Selector

  • Each of the four player setup blocks now includes a Gender dropdown — M — Men's (default) or F — Ladies'
  • Changing the gender immediately recalculates that player's CH and PH using the correct tee rating
  • Each player's gender is independent — mixed groups (e.g., three men and one woman) are fully supported
  • The CH / PH display line shows the tee rating used, e.g.: CH: 12 | PH: 12 (Red L 70.8/129) — the L confirms ladies' ratings are active

Bug Fix — Gender Not Persisting in Card State (v95.27)

After setting a player's gender to F — Ladies', the CH still calculated against men's ratings. The gender selector was wired correctly but the selection was not surviving card save/restore cycles.

Root Cause

  • saveCurrentCardToStore() never wrote gender to the card's player state — it was silently discarded on every save
  • loadCardFromStore() never read gender back — the HTML select defaulted to M before calcHcp() fired, overriding any selection the user had made
  • Since saveState() fires at the end of calcHcp(), every GHIN or tee entry triggered a save that overwrote gender to undefined

Fix

  • saveCurrentCardToStore() now writes gender per player alongside name, GHIN, and tee
  • loadCardFromStore() now restores the gender select before calcHcp() fires — ensuring the correct CR/Slope is used on the very first calculation after load
  • Gender persists correctly through card switches, Print Both, Print All, and page reloads

Bug Fix — Ladies' Ratings Not Reaching calcCH() (v95.28)

After v95.27, gender persisted correctly and calcCH() received gender='F' — but the ladies' CR/Slope values were still undefined inside the function, causing the men's ratings to be used as fallback. CH still read incorrectly for female players.

Root Cause

There are two TEES= assignments in the code:

  • Global initializer — runs once on page load using the default course (Tampa Palms). This is the assignment that getTee() reads from during normal play.
  • applyCourseProfile() — only runs when the user changes the course dropdown. Since Tampa Palms is pre-selected, this never fires during a normal session.

The v95.26 patch added lRating / lSlope to the applyCourseProfile() assignment only. The global initializer — the one that actually matters — was left unchanged, stripping ladies' ratings before they could reach getTee().

Fix

  • Global TEES initializer updated to include lRating:t.lRating, lSlope:t.lSlope alongside rating and slope
  • Both TEES= assignments now pass ladies' ratings through — page load and course change paths are both correct
  • getTee() now returns complete tee objects with ladies' data available to calcCH()
